Isolated dev sandboxes for a Windows team

Each developer runs their own AI coding agent and Docker Compose stack inside a private Linux sandbox on their own laptop. A single shared Postgres on the on-prem Linux server holds everyone's data. Nobody can break anyone else's work, or the server.

The goals

1Windows team, Linux server

Developers work from Windows laptops; builds and containers run on real Linux.

2One shared database

A common Postgres container on the on-prem server, with a separate database per developer.

3Independent Compose stacks

Everyone runs their own docker compose without port, image or volume clashes.

4No one breaks the machine

A mistake or a misbehaving agent stays inside one developer's sandbox.

5No WSL2

Sandboxes are lightweight Linux virtual machines managed by Docker's sbx tool.

The approach

Install sbx (Docker Sandboxes) on each Windows 11 laptop. It starts a small Linux virtual machine per project, with its own kernel and its own Docker daemon. The agent and the developer's Compose stack run inside it. Outbound network traffic is denied by default and goes through a proxy, so the sandbox can only reach what the team explicitly allows, which includes the shared database on the server.

Detail: architecture · what a sandbox is

Benefits

  • Strong isolation. Each sandbox is its own virtual machine with its own Docker daemon, so there is no shared Docker socket and no way to reach another developer's containers.
  • Safe to give an agent real autonomy. The agent can install packages and run containers inside its sandbox without touching the laptop or the server.
  • Independent by default. Two developers can run the same Compose project with no port, image or volume collisions.
  • Linux parity. The code builds and runs on Linux, as it will in deployment, even from a Windows laptop.
  • Reviewable network access. One allowlist script is the whole list of hosts a sandbox can reach.
  • One shared failure domain, well fenced. The only shared piece is Postgres, with a separate database and role per developer, TLS, connection limits and backups.
  • Low cost. The sbx tool and local compute are free; only central governance is a paid tier.

Simple setup

Four steps cover the goals above. The pages linked under each step have the full instructions and the options.

1Enable and install on each laptopIT once, then the developer

IT turns on one Windows feature (needs admin and a reboot; no WSL2). The developer then installs sbx without admin and signs in with a Docker account created with their company email.

# IT, elevated PowerShell, once per laptop
Enable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform -All

# developer
winget install -h Docker.sbx
sbx login
sbx secret set anthropic      # model-provider key, kept out of the sandbox

Details: Windows and admin · onboarding checklist

2Start the shared databaseops, once

Run Postgres 18 on the server with TLS and a subnet-restricted access file, apply the baseline hardening, then create one isolated database per developer.

cd config
export POSTGRES_PASSWORD=<strong-secret> DB_BIND_ADDR=<server-lan-ip>
docker compose -f shared-db.compose.yaml up -d
docker exec -i shared-postgres psql -U postgres -v ON_ERROR_STOP=1 < db-baseline.sql

# per developer
docker exec -i shared-postgres psql -U postgres -v ON_ERROR_STOP=1 \
  -v dev=alice -v pw="$(openssl rand -base64 24)" < provision-developer.sql

Details (certificates, firewall, backups, offboarding): runbook, section B · Compose and the shared DB

3Allow only what the project needsdeveloper

Choose the Locked Down network preset on first run, then allow the database, your model provider, package registries and Git.

# from the repo root
sh config/allowlist.sh <db-host> anthropic

Details: networking and policy

4Create the project environment and startdeveloper

Copy config/sbxenv.yaml beside the project (not inside it), fill in the project name and database URL, then create and attach.

sbx env plan      # preview
sbx env run       # create the sandbox and attach the agent

Work on the project folder from Windows as usual; the sandbox sees the same files. Inside the sandbox, run docker compose up against the shared database.

What to know before relying on it

Still to be tested. The path from a sandbox to the Postgres server (raw TCP on port 5432 through the sandbox proxy) is the design's main assumption and has not been verified yet. The troubleshooting steps are the test.
  • One-time admin is needed. No WSL2, but each laptop needs the Windows Hypervisor Platform feature enabled once.
  • The agent can see its database password. A Postgres credential cannot be hidden from the sandbox, so each developer gets a low-privilege role that can only touch their own database.
  • Agents can be steered by what they read. Keep the allowlist short and use clone mode for code you do not trust. See security.
  • There is overhead. Keep dependencies and build output off the mounted folder. The performance doc has a benchmark to run on one real project first.
  • sbx moves fast. Its environment-file feature is experimental; pin one version for the team and recheck the docs when you upgrade.
